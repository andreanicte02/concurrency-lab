01

The lost update

Several threads run count = count + 1 on the same variable. It looks like one step, but the CPU does three: read the value, add one, write it back. If two threads read before either writes, one increment disappears.

      The fixes 
      // broken: read-modify-write race
count = count + 1;

// synchronized: one thread at a time
public synchronized void increment() { count = count + 1; }

// ReentrantLock: always unlock in finally
lock.lock();
try { count = count + 1; } finally { lock.unlock(); }

// AtomicLong: lock-free compare-and-swap
count.incrementAndGet();

      02

      The overdrawn account

      Customers at different ATMs withdraw from the same account. Each ATM checks if (balance >= amount) and then subtracts. Between the check and the update, another ATM can do the same check and see the same money — so the bank hands out cash that isn't there. This is the check-then-act race.

      The fix 
      // The check and the update must be one atomic step.
public synchronized boolean withdraw(int amount) {
    if (balance >= amount) {
        balance = balance - amount;
        return true;
    }
    return false;
}

      03

      The sleeping barber

      One barber, one chair and a small waiting room. When nobody is waiting the barber sleeps; an arriving customer wakes the barber, sits down, or leaves if every chair is taken. Naive versions busy-wait (burning a CPU core) or lose a wake-up and deadlock. This one uses a bounded BlockingQueue as the waiting room: offer() atomically claims a chair, and the barber sleeps inside take().
